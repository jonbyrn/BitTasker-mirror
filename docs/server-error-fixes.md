# Fix Plan: SvelteKit Deployment Cache Inconsistency

## Root Cause (Verified)

- Deployment target: **Cloudflare Pages** with `functions/_middleware.ts`.
- Pages serves all assets (including `index.html`) with `Cache-Control: public, max-age=0, must-revalidate` + `ETag` by default.
- On every new deployment, Pages automatically invalidates its edge cache for changed assets.
- **The actual problem is not browser-cached HTML.** The problem is **in-memory stale JS**.
- When a user has the app open in a tab (or the tab is restored from bfcache), the SvelteKit client router intercepts navigation clicks and lazily calls `import('/chunk.[oldHash].js')`. If a deployment occurred and replaced the chunk hashes, that URL returns 404. The user sees a "server error" modal.
- A soft F5 refresh fixes it because `location.reload()` sends `Cache-Control: max-age=0` (conditional GET), Pages returns new `index.html` with new chunk hashes, and the app re-bootstraps cleanly.
- The error is **intermittent** because it only triggers when the user navigates to a route they hadn't visited in the current session, AND a deployment occurred since the app was loaded.

## What Does NOT Apply Here

- `static/_headers` file: **has no effect**. Cloudflare Pages docs explicitly state custom headers in `_headers` are not applied to responses generated by Pages Functions. This project uses `functions/_middleware.ts`, so `_headers` is bypassed for every response.
- `workers-site/index.js` cache TTLs: not active for the current Cloudflare Pages deployment. Relevant only for the future Workers Sites migration.
- Service worker interference: no service worker exists in this project.
- Toast / version polling (`version.pollInterval`): valid for long-running active sessions but does not cover the primary failure scenarios (stale tab restored from bfcache, tab open during deployment).

## Implemented Fix

### Architecture

++Two-layer catch for chunk load failures, using a version-scoped++ `sessionStorage` ++key for loop prevention:++

```
Chunk 404
    │
    ▼
vite:preloadError (window event — fires before SvelteKit's error handler)
    │  Primary catch in +layout.svelte onMount
    │  event.preventDefault() → suppress propagation
    │  sessionStorage key NOT set → reload once
    │  sessionStorage key SET → do nothing, let error propagate
    │
    ▼ (if not suppressed)
handleError in hooks.client.ts
    │  Secondary catch (inside handleErrorWithSentry wrapper)
    │  Sentry captures the error first (via handleErrorWithSentry)
    │  sessionStorage key NOT set → reload once
    │  sessionStorage key SET → surface error to user (real bug, not stale cache)
```

### Version-scoped Key

The `sessionStorage` key is `chunk-reload-${__BUILD_VERSION__}`. `__BUILD_VERSION__` is a string injected at build time via Vite's `define`. It is:

- `CF_PAGES_COMMIT_SHA` on Cloudflare Pages CI builds (unique per deployment).
- `Date.now().toString()` as fallback for local builds (unique per build command run).

This scoping ensures:

- A flag set by deployment A (`chunk-reload-abc123`) never blocks a reload triggered by deployment B (`chunk-reload-def456`).
- Within the same deployment, a flag IS set after the first reload, preventing infinite reload loops if the error is a real bug in the current build (not a stale-cache issue).
- `sessionStorage` is per-tab, not shared. Multiple open tabs behave independently.

### Files Changed

#### `vite.config.ts`

Added `__BUILD_VERSION__` to the `define` block:

```typescript
__BUILD_VERSION__: JSON.stringify(
    process.env.CF_PAGES_COMMIT_SHA ?? Date.now().toString()
),
```

#### `src/app.d.ts`

Added global TypeScript declarations:

```typescript
const __BUILD_VERSION__: string;

interface VitePreloadErrorEvent extends Event {
	payload: Error;
}

interface WindowEventMap {
	'vite:preloadError': VitePreloadErrorEvent;
}
```

- `__BUILD_VERSION__` makes the build-time constant visible to TypeScript across all files.
- `VitePreloadErrorEvent` types the `event.payload` property (the original import error).
- `WindowEventMap` extension means `window.addEventListener('vite:preloadError', handler)` is correctly typed without casting.

#### `src/routes/+layout.svelte`

Added `vite:preloadError` listener inside the first `onMount`, before the existing global error handlers:

```typescript
const CHUNK_RELOAD_KEY = `chunk-reload-${__BUILD_VERSION__}`;

const handlePreloadError = (event: VitePreloadErrorEvent) => {
	if (!sessionStorage.getItem(CHUNK_RELOAD_KEY)) {
		event.preventDefault(); // suppress propagation to unhandledrejection
		sessionStorage.setItem(CHUNK_RELOAD_KEY, '1');
		location.reload();
	}
	// flag set → persistent error → propagates to handleError → Sentry
};

window.addEventListener('vite:preloadError', handlePreloadError);
```

Cleanup in the `onMount` return:

```typescript
return () => {
	window.removeEventListener('vite:preloadError', handlePreloadError);
	// ... existing cleanup
};
```

**Why `event.preventDefault()`**: Without it, after `location.reload()` is called, the import error would also propagate to `window.onerror` / `unhandledrejection` and then to SvelteKit's `handleError`, potentially showing the error UI for a split second before the reload completes. `preventDefault()` suppresses this.

**Why primary catch is in `+layout.svelte` not `hooks.client.ts`**: `vite:preloadError` fires synchronously before SvelteKit's error boundary. It is the earliest possible interception point. `handleError` is downstream and not guaranteed to receive all chunk load failures (some may be swallowed by the router before reaching it).

#### `src/hooks.client.ts`

Added chunk error detection inside the `handleErrorWithSentry` callback (secondary catch):

```typescript
export const handleError: HandleClientError = handleErrorWithSentry(({ error }) => {
	const message = (error as Error)?.message ?? '';
	const isChunkError =
		message.toLowerCase().includes('failed to fetch dynamically imported module') ||
		(error as Error)?.name === 'ChunkLoadError';

	if (isChunkError) {
		const CHUNK_RELOAD_KEY = `chunk-reload-${__BUILD_VERSION__}`;
		if (!sessionStorage.getItem(CHUNK_RELOAD_KEY)) {
			sessionStorage.setItem(CHUNK_RELOAD_KEY, '1');
			location.reload();
			return { message: 'Reloading to apply updates…' };
		}
		return { message: 'An error occurred loading the application. Please refresh.' };
	}

	return { message: 'Whoops! An error occurred' };
});
```

**Sentry timing**: `handleErrorWithSentry` captures and queues the Sentry event before our callback runs. `location.reload()` may interrupt the outgoing Sentry network request. This is acceptable — Sentry uses `navigator.sendBeacon` as a fallback transport on page unload which can persist through navigation, so events are often sent successfully. For the persistent-error branch (flag already set), the page is NOT reloaded, so Sentry always sends successfully.

## Loop Prevention Logic (Full Flow)

| Scenario                                                                      | `sessionStorage` key            | Primary (`vite:preloadError`)             | Secondary (`handleError`)          | Outcome                                 |
| ----------------------------------------------------------------------------- | ------------------------------- | ----------------------------------------- | ---------------------------------- | --------------------------------------- |
| Stale JS after deployment, first chunk failure                                | Not set                         | `preventDefault()` + set key + reload     | Not reached                        | User gets fresh `index.html`, app works |
| Same stale JS, second chunk failure after reload (should not happen normally) | Set                             | Does nothing (propagates)                 | Reload blocked, surfaces error     | User sees "An error occurred…"          |
| Real bug in current build, first chunk 404                                    | Not set                         | `preventDefault()` + set key + reload     | Not reached                        | Reload, same bug, key now set           |
| Real bug in current build, second chunk 404                                   | Set                             | Does nothing (propagates)                 | Surfaces error, Sentry captures it | User sees error, Sentry reports it      |
| New deployment (new `__BUILD_VERSION__`)                                      | Old key exists, new key not set | `preventDefault()` + set new key + reload | Not reached                        | Reload works, old key irrelevant        |

## Future: Workers Sites Migration

When migrating to Workers Sites (`workers-site/index.js`), one additional change is required:

- Line 66 of `workers-site/index.js` sets `htmlBrowserTTL = 60 * 30` (30-minute browser cache for `index.html`).
- `location.reload()` sends `Cache-Control: max-age=0` (like F5), which forces revalidation regardless of the cached `max-age`. Combined with the `purge-cache.js` edge purge that runs after every CI deployment (`purge_everything: true`), this works correctly in CI.
- However, local `wrangler deploy` runs skip the purge (`CI !== 'true'`). For consistency, changing `htmlBrowserTTL` to `0` in `workers-site/index.js` is recommended when the migration is done — this makes `index.html` always revalidate without relying on the purge.
- The client-side fix implemented here (the two-layer reload strategy) works for both Pages and Workers Sites without modification.
