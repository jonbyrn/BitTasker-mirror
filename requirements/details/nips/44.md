# NIP-44: Encrypted Direct Messages v2

NIP-44 is an improved version of NIP-04 for encrypted direct messages in Nostr. It addresses several security concerns present in NIP-04 and provides a more robust encryption scheme.

## Technical Details

### Key Improvements over NIP-04

1. Better Lock System (ChaCha20-Poly1305 instead of AES-CBC)
   - Uses a newer, faster way to scramble messages
   - Includes a "tamper seal" - if someone tries to modify the message, you'll know
   - Like having both a lock and a seal on your envelope

   Technical details:
   - Uses ChaCha20-Poly1305 instead of AES-CBC
   - ChaCha20 is a modern stream cipher designed for better performance in software
   - Poly1305 provides authenticated encryption (AEAD) to prevent tampering
   - No padding oracle attacks possible (unlike CBC mode)

2. Proper Key Derivation
   - Instead of using your key directly, it creates special sub-keys for different purposes
   - Makes it harder for attackers to break in even if they get one key

   Technical details:
   - Uses HKDF (HMAC-based Key Derivation Function) to derive encryption keys
   - Separate keys for encryption and authentication
   - Includes version-specific salt to prevent cross-protocol attacks

3. Better Padding Scheme
   - Hides the real length of your message
   - Makes all messages look the same size to outsiders
   - Like using standard-sized envelopes regardless of the letter inside

   Technical details:
   - Length prefix to prevent padding oracle attacks
   - Power-of-2 based padding to hide message length patterns
   - Explicit length validation during decryption

## Implementation Details

### Conversation Key Generation
```typescript
// Create a shared secret that only you and the recipient can generate
export async function getConversationKey(pubkey: string): Promise<Uint8Array> {
    const sharedPoint = secp256k1.getSharedSecret(pubkey, pubkey);
    const sharedX = sharedPoint.slice(1, 33); // Take x coordinate only
    return hkdf(sha256, sharedX, new TextEncoder().encode('nip44-v2'), '', 32);
}
```
- Uses secp256k1 shared secret computation
- Takes only the x-coordinate (first 32 bytes after prefix)
- Derives a 32-byte key using HKDF with NIP-44 v2 salt

### Message Key Derivation
```typescript
function getMessageKeys(conversationKey: Uint8Array, nonce: Uint8Array): {
    chachaKey: Uint8Array;
    chachaNonce: Uint8Array;
    hmacKey: Uint8Array;
}
```
- Takes conversation key and 32-byte nonce
- Uses HKDF to derive three keys:
  1. ChaCha20 encryption key (32 bytes)
  2. ChaCha20 nonce (12 bytes)
  3. HMAC key (32 bytes)

### Message Format

The encrypted message consists of layers:
1. Version byte (0x02 for NIP-44 v2)
2. 32-byte nonce
3. Encrypted padded message
4. 32-byte HMAC tag

### Padding Scheme

Technical view:
1. Message is padded to a standard size using power-of-2 based padding
2. ChaCha20 stream cipher encrypts the padded message
3. Poly1305 authenticator creates a MAC (Message Authentication Code)
4. 32-byte random nonce ensures unique encryption

Messages are padded to hide their exact length:
1. Length is stored as 16-bit big-endian prefix
2. Message is padded to next power-of-2 chunk size
3. For messages ≤ 32 bytes: padded to 32 bytes
4. For messages > 32 bytes: padded to next chunk size (chunk = nextPower/8)

## Security Considerations

1. Forward Secrecy
   - Not provided by default
   - Can be achieved by rotating conversation keys

2. Replay Protection
   - 32-byte random nonce prevents accidental reuse
   - Application layer should implement additional replay protection

3. Message Authentication
   - HMAC with AAD (Additional Authenticated Data) prevents tampering
   - Nonce is included in AAD to bind it to the ciphertext

4. Key Separation
   - Different keys for encryption and authentication
   - Version-specific salt prevents cross-protocol attacks

## Usage Example

```typescript
// Generate a conversation key -  Start a private conversation
const conversationKey = await getConversationKey(recipientPubkey);

// Create a unique number for this message
const nonce = crypto.getRandomValues(new Uint8Array(32));

// Encrypt a message
const encrypted = await encrypt("Hello, Nostr!", conversationKey, nonce);

// Decrypt a message
const decrypted = await decrypt(encrypted, conversationKey);
```

## Comparison with NIP-04

| Feature           | NIP-04        | NIP-44                     |
|-------------------|---------------|----------------------------|
| Cipher            | AES-CBC       | ChaCha20-Poly1305          |
| Key Derivation    | Direct use    | HKDF                       |
| Authentication    | None          | HMAC-SHA256                |
| Padding           | PKCS#7        | Length-prefix + power-of-2 |
| Nonce Size        | 16 bytes      | 32 bytes                   |
| Version Control   | No            | Yes                        |
| Forward Secrecy   | No            | No                         |


## Current Limitations

1. Messages are secure in transit, but if someone gets access to your device and your keys, they can read past messages. Future versions might add features to prevent this.

2. The system relies on both people having their keys secure. If either person's keys are compromised, the conversation is no longer private.

3. No forward secrecy - if someone gets your keys in the future, they can read all past messages. This could be improved in future versions by regularly changing conversation keys.
